# A7 从开书到远端回读

命令由 GPT 在解包后的目录执行。可使用 python3 novel.py --root 小说目录 子命令。示例中的值须从实际任务取得。恢复先读目标仓库的默认分支、book/state.json、最新冻结记录、online/index.json 和在途目录，核对书名、book_id、edition、版本和仓库链接。

## 1　部署与选题

先在解包目录跑 package-check。读取 GitHub 实际默认分支、头提交、目录和原启动文件。遇到旧 A、B、V4 或已有正文先依项目原说明继续。有 README 等中性文件的空白工作区可做增量安装，同名说明先归档到无冲突路径，保留无关文件。若仓库确实没有任何分支和提交，先用 GitHub Contents create_file 以包内实际 README 建第一个提交，再读取生成的默认分支和 HEAD。单次 404 或超时不能判为空仓库。首提交不确定先回读。每次写回使用下文第 5 节的办法。

部署后执行 package-check 和 init --repository 实际目标仓库 --branch 实际默认分支。已知平台可加 --platform。第一次部署生成的 book_id 只用一次。初始化后保存并回读 state 和 index。新聊天接手已有身份直接恢复。参考库、管理仓库、系统母版均禁止作为目标。

按作者选的平台，核对当前官网的频道、开书流程、直发或内投、样稿长度、原创和 AI 使用规范。在计划里分开记后台/官方要求、实际能看到的当期同类开头，以及待核事项。无法确认送审篇幅时以本地一万汉字作内部试读，注明理由。平台计数有自己的口径。纵横直发在 2026-11-18 查到的公开指南为满 1 万字自动进入签约审核。下次开书再查，不能据此推定编辑实际读了多少。来源 https://doc.zongheng.com/welfare/zongheng 。

读 XS-KU 当次默认分支与 catalog.json。按 CRAFT.md 给若干明显不同的原创选题，让作者选。研究和拟定候选均不写正式章节。作者选定后 configure --title 选定书名 --platform 平台，照 templates/plan.md 整理全书走向、前五章和自然叙事的大纲，写入 book/plan.md。保存已选择的题目和阶段，等待“开始写”。

## 2　确认开始后，先用两场正文试出开法

在参考库同一固定 commit 的 tree 取原文路径和 blob，按 catalog 的 family_id 去重。若有同平台同类原作优先取用。元数据不能代替原文。使用 GitHub 文件工具保留原始换行与编码，把原文件在临时目录读给自己看。大文件可从该固定提交按 Git blob 读取或用完整只读 Git 检出。不要把参考全文写入新书。先取一个能读到后果的范围，依需要另读前后段。

工具会核对完整原文件的 Git blob，再按可复现的段号取样。文件开头如有书名也占一段。下列命令中的大写词是 GPT 替换的实际值。

    python3 novel.py excerpt --file 临时原文件 --blob BLOB --first 起段 --last 止段
    python3 novel.py sample --file 临时原文件 --blob BLOB --first 起段 --last 止段 --commit COMMIT --source-path 库内原文路径 --family 实际作品组 --lesson '一个具体的选择为什么改变' --limit '这个办法在哪种情况下会写坏'

每本至少登记一处完整的决定与后果，另有实读范围可记在计划中。需要非 UTF-8 编码时两条命令均带 --encoding 实际编码。程序验证字节和范围；commit、路径与 blob 的配对由执行者回查同一 Git 树。研究暂时取不到原文时，先完成能核实的选题和计划，恢复时接着读。

在 book/opening/a.txt 与 b.txt 各写一个能独立阅读的原创场面，可共用人物与处境。一个让主角先行动，另一个可以从利益相反的人抢先行动写起。区别须涉及决定和后果；仅改第一行、叙述人称、天气或放大嗓门，重新试写。一般各 350—800 汉字，程序只排除明显空白、过短或两份同文的材料。两个都撑不起两三场戏，换事件再试。book/opening/choice.md 记录哪一个值得保留，另一份在哪个瞬间失掉人物，以及保留方案在首个送审窗口内能给读者什么。不要把试稿拼接成正式章。

    python3 novel.py audition --pick a --window 10000 --basis '实际平台、渠道、核查日期和来源；无法核实时注明内部取样' --author-started

--pick 按实际结果选 a 或 b。--window 用本书当次核查的额度作本地汉字近似，--author-started 只在已有作者开写授权时使用。试稿、理由和参考依据成为本书开篇快照。先提交并回读，使新聊天可以接着做首章。其后的“下一章”无需重做试写或再向作者确认。

## 3　一个请求只办一章，允许同日多章

先运行 status、context、verify。读最近正式正文、章后记忆、计划与当前 draft。人物重逢或事实有争议时回到相关旧章。运行 begin --request 实际稳定请求编号。重试复用原编号；遇到 resume 使用返回的原任务与章号；already_frozen 核对该章的远端提交后交付。发现只有草稿而无 task.json，先从同书 Git 历史核对并恢复，保留原草稿。请求号不是调度平台的执行号。

工作目录为 book/work/CH001 等。draft.txt 中只写正文，UTF-8，章名在 freeze 时另给。每章 5500—6500 汉字。先写那个无法两全的决定和别人当场做出的反应，再补足场景需要的过程。允许沉默、笑话、慢场与失败。半章、完整候选及中断前各保存当时实有的草稿、task.json 和续写位置。新聊天取最近提交，不从头再编一版。

写完脱离大纲，先看正文。packet 只输出开头连续正文，按汉字截断，章节标题不占预算。前五章每次累计读从第一章到本章的全文；第一批达到送审窗口时另读实际截本。每五章再连读最近五章，其他章节按自身问题选择阅读位置。

    python3 novel.py packet
    python3 novel.py packet --han 1200

问自己从哪里开始只想往下划、最早能认出本书独有卖点的是哪一场、主角实际赢回或失去了什么。题材专有名词拿掉，人物决策若仍可原封塞进别的书，优先改这场戏。高潮之后允许一盏灯、一顿饭就收住，前提是读者清楚这份安宁是谁换来的，下一步是谁会为此采取行动。

## 4　实际返修与定稿

editorial.md 写最有理由的一到三个问题、改了哪里、遗留什么。memory.md 写下一章需要接续的事实、人物知道或误信什么、谁还在付上次选择的代价，标章号。用 python3 tools/prose_check.py 查字面重复，重读候选位置。两章一直用同一办法解决矛盾，即使一个字没重，仍然值得重写。结构不成立时先换事件或代价，不凭润色宣告已解决。

第一至第五章、累计第一次跨过试读窗口的章、以后每第五章，由 GPT 在当章工作目录生成 reading.json。只引用本书正文，每条短引 4—120 字，须在原文原位置连续出现。用当前实际选择替换以下示意文字。人物可以通过同一个场面同时带来几种收获，程序不评价感染力。

    {
      "verdict": "ready",
      "friction": {"quote":"当章最可能让人停下的原句","why":"读者在等什么，这里付出了多少耐心，修后还剩什么"},
      "payoff": {"quote":"当章结果已发生的原句","why":"哪个人因此得到或失去了什么"},
      "next":"读者看完具体会担心或期待什么；完结可写最后留下的感受",
      "front": {"quote":"第一章开头一千二百汉字内的原句","why":"读者如何认出主角、欲望和机会"},
      "previous": {"quote":"上一冻结章的原句","why":"上一次选择怎样造成这章的难处，解法有何变化"},
      "window": {
        "promise":{"chapter":1,"quote":"截止前出现的实际原句","why":"到这里已能看懂哪种特别的困境"},
        "delivery":{"chapter":1,"quote":"人物已经得到或失去某样东西的原句","why":"转折由谁的哪个决定造成"},
        "order":"setup_first",
        "effect":"逐字摘录含 delivery 短引的现场正文，最多六百字符，必要时保留前后句"
      }
    }

首章冻结前就填 window。在首章与本书窗口中取先到的截止位置。如果下一章或以后的某章才写满窗口，届时从第一页重新读到实际截点，再填一次。front 用于首章，previous 从第二章开始。各短引在所标章号的可见部分要能唯一定位。顺叙写 setup_first，先展示后果再揭起因写 result_first。两段在阅读顺序上各有自己的位置。effect 只保存现场原话，短引本身足以呈现结果时可直接使用。自己对谁得失的解释写在 delivery.why。把这两项并排读一遍，假如原文只写了准备去翻谱，解释却称已经拿到领班铜牌，就按原文退修。程序核对出处、顺序和大段重复。读者为什么会在乎这两段，由执行者读正文判断。

首章读两遍。第一遍关掉大纲、试稿说明和书库笔记，只读 packet --han 1200，再读实际可见全文。用人物自己的难处说出“此刻他要什么，为什么等不起”，留心第一处会顺手划走的地方。第二遍回看那两段，把还没发生的打算逐一拿掉，说明眼前已有的收获、失去或认识变化。换个书名，这个场面若仍然只是在交接、登记、解释设定，问是谁因这一场改了决定。若只能靠下一章或大纲补答，记录 revise，在本章里换掉那场戏并重新实读。读者发现秘密、两人第一次肯坐到同一张桌子、赢回一小笔钱都可以成立。窗口超过一章时再问首章的选择在后续可见页怎样影响了别人。

遇到挡住定稿的问题，先用 assess --expect 当前正式状态哈希 --decision revise 记录草稿及具体问题。可以是短稿。同一退回稿重试按同一份处理；三种不同退回稿之后再评仍需返修会保存 blocked。回到当前候选实质返修，重新跑检查和试读，再决定。一个请求内主动做完，必要时可重写整场。最多三轮实质返修后它还站不住，就保存原任务与卡住的那场戏，让下次从这里恢复；不要偷偷改旧章、另开一本、重置次数或把问题写成已经解决。续写在 progress.md 记录实际轮次和最近修改位置。

    python3 novel.py assess --expect STATE_SHA256 --decision ready
    python3 novel.py freeze --expect STATE_SHA256 --request ORIGINAL_REQUEST --title 实际章名
    python3 novel.py verify
    python3 novel.py index

只有 ready 对应的正文、编辑意见、计划、记忆与当次试读相符才能冻结。改过文字或试读判断就重新 assess。生成冻结记录和不可变快照，原子推进 state；中断后同一个请求只采用一次。修改未冻结候选和未来路线，不覆盖旧章。

## 5　GitHub 保存与实读

每轮读实际默认分支、HEAD 和 tree，比对作品身份与当前请求。增量提交，保留 base tree，并用该次 HEAD 为父提交；更新分支时 expected_sha=读取的头，force=false。并发失败先阅读新头和改动，再决定恢复或合并，禁用旧 tree 强推。操作超时先查远端是否已有当前请求结果。阶段进度和草稿要随时有可恢复的实际内容。

回读固定新提交的 state、index、正文、冻结记录及其引用的编辑快照，核对书名、book_id、章号、请求、正文 SHA256 和记录链。在可用工作区运行 verify。对不上就报告哪项仍未回读；处理完才能说已冻结并保存到 GitHub。读者端可沿现有阅读格式读取。保持平台发布状态 unconfirmed，除非作者另给真实平台记录。

## 6　投稿资料与结果

作者要投稿资料时，用已选平台当期真实表单。交付可直接填的频道、分类、标签等字段，简介、讲到结局的自然叙事大纲、指定尺寸的实际封面和 TXT。未知项标待核，作者自行投稿。若后来带回复核结果，把作品、渠道、日期、可定位版本和原话记在书内独立反馈文件。一次拒签或一次签约只说明这次投稿结果，系统调整留给后续新稿验证。
