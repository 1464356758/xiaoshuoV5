# V6.2.1 正式使用前验收

核查日期：2026-11-14，北京时间。范围是新书引擎、开书/续写指令、交付包和工作台兼容读取，不改任何现有小说正文。本轮保留V6.2方法与五章候选，没有以换书或重复润色冒充新验证。

## 已复现并修复

| 环节 | 修复前的实际问题 | 修复与回归 |
| --- | --- | --- |
| 部署目标 | .git后缀绕过系统/参考库禁写检查，非法分支仍生成身份；软件漏拦XS-GL | 先规范仓库链接并校验分支，前后端拦截同类保护目标；错误时不生成state |
| 草稿恢复 | task丢失后，新请求可能接管旧工作文件 | 保留草稿并拒绝重新绑定；指令明确按真实历史找回原任务 |
| 冻结中断 | state已经采用但索引写失败，同请求begin重试仍留旧目录 | already_frozen路径修复索引，再核验原结果 |
| 定稿材料 | freeze信任已有ready记录，没有再次检查实际正文、UTF-8和附件内容 | assess、freeze、verify复用真实材料验证；短正文、空意见/记忆、无效UTF-8不得推进state |
| 审读快照 | 哈希一致时，可变工作文件可能被引用为正式审读依据 | 只接受以内容哈希命名的不可变对象 |
| 错误反馈 | JSON根节点为数组时出现未处理traceback | 明确报告文件应为对象并保留原文件 |
| 阅读正文 | 前端解码去掉BOM、改写CRLF，造成正确冻结文件也校验失败 | 按原始UTF-8字节内容计算哈希；前后端使用同样汉字区间 |
| 读取完整性 | 索引标题与state不一致、旧章实际记忆附件丢失仍可能读过 | 对照章序/标题/进度/路径，读取并核验正文与三份实际附件 |
| 今日更新 | 当天已冻结一章后再起草下一章，被误报尚未更新 | 分开保留最新正式章与待续草稿，今日状态仍为已更新 |
| 即时续写 | 手动模式也要求有效定时时间，清空时间后无法复制 | 只有定时模式验证时间；已加入小说时即时模式不依赖时间 |

上述核心与前端问题先加入失败用例再修复，不把所有子用例各算一个BUG。另加构建保护：旧界面关键适配点变化时直接停止打包，避免静默漏装修复。

- 生产生成的GitHubClient通过离线HTTP文件夹复现BOM/CRLF、旧章附件缺失、篡改标题、同日下一章草稿与手动时间边界。

## 指令修订与恢复边界

完全空GitHub仓库没有HEAD，补齐了先用Contents接口创建实际README首提交、再读取真实HEAD/tree增量部署的步骤，依据[GitHub官方说明](https://docs.github.com/en/rest/guides/using-the-rest-api-to-interact-with-your-git-database)，未另建真实仓库实测。404/409不能单独作为仓库为空的证据。

写作改为实际分段落盘，约半章同步草稿与原任务，完成正文和主动中断时再保存。突然停止仍可能丢失最后同步后的内容。远端写操作结果不明先回读；冲突不能只换expected_sha重发旧tree。

## 正式使用方式

1. 新建一部书：新的GPT工作聊天，附加本版初始化系统包.zip，给独立新书仓库；也可复制包内启动新书.txt或软件的新书指令。
2. GPT核验并部署后，选平台、选题，说“开始写”。前五章整体设计；每章5500—6500汉字，默认150章。没有每日一章限制。
3. 后续直接说“下一章”。存在实际草稿时先续完原目标；完成后给本章正式文件与真实提交。网页是管理与阅读端，指令须发给GPT才会写作。

旧书继续原引擎；本次没有迁移旧书、修改冻结正文、另建日程或请求模型API。
