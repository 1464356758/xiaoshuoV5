# 个人端任务指令 1.4.5

个人端“日更指令”用于配置本书唯一任务，“更多 → 补更指令”用于核查并接续当前未完成目标。两种指令共用同一套逐阶段写作、恢复和验收要求。

## 日更配置

输出明确分为“本次配置”和带起止标记的“长期任务指令”。GPT只将长期部分保存为任务prompt，绑定经过核实的仓库、分支与book_id。查找同书已有任务并复用；核对时区、日程、启用状态、反馈对话及平台实际返回的下次时间。缺失运行元数据不能靠提示词补造。

不把配置时的当前章次、候选文件、旧锁编号或聊天总结写成永久状态。所有后续运行都重新读GitHub。管理清单的勾选只控制今日更新查询，不作为任务写作权限或完成证据。

## 每轮执行

1. 核实最新state、workflow、active、任务配置和真实运行归属。首次运行没有active记录与读取失败分开处理。
2. 读取最新HEAD及commit.tree.sha，以该树SHA作为base_tree_sha增量提交独立请求；保留单一父提交、expected_sha与非强制更新。先发preflight，再查该source_sha的Actions和不可变result。
3. begin确定唯一目标，回读锁以后写作。遵守本书现有completion_policy；per_trigger按现行协议提供稳定trigger_id，不自动改变策略。
4. 生成资料后继续写整章，可按场景保存同章工作稿和进度。进度含真实run_id、阶段、正文路径/哈希/字数、已完成场景及下一步，接续时对照实际稿件与result。进度文件不证明采用。
5. 实际完成反向提纲、限信息审读、八项证据及叙事检查，最多三轮局部修订；到期回看在冻结前完成。finalize通过后回读正式正文、记录、回执与哈希。

预检通过仅证明工具链可用；tools_completed仅证明本批工具成功；任务平台completed或Actions绿色不能证明章节已写完。只有chapter_completed及正式证据回读一致才报告“本轮章节已完成”。真实故障保留原目标与检查点，报告“本轮章节未完成”和具体缺口。

## 补更与恢复

普通聊天先核实确有未完目标，区别已有授权的operator_recovery.status=ready维护检查点与普通blocked/running。普通旧执行必须核实原控制者的确切平台运行终态及相关执行器作业终态；无法核实就保留待核，不能超时抢锁。ready只消费已有维护授权，不能自行制作授权。

条件成立后优先使用本书原有任务的立即运行入口。任务未启用、入口未提供或调用拒绝时报告实际缺口，不另建任务、不改日程、不伪装automation controller或借用旧session。发起成功只证明已提交补更请求；结果必须匹配本次新运行，不能展示旧结果来证明本次完成。

已经完成并且证据齐全则停止，不额外新开一章；仅缺回执时按recovered_completion恢复证据。原有任务中的真实执行继续使用本轮controller，经协议合法恢复同一目标，不清空候选和返修次数。

## 实际能力边界

网页负责生成指令与核验GitHub。复制指令后须发送到本书GPT聊天实际更新任务；网页发布不会改动已经创建的计划。GitHub执行器负责文件工具和验证，没有再次唤醒GPT的能力。此次修复使指令和实际能力一致，不代表已增加自动补跑服务；稳定日更仍须以真实完整运行及中断恢复验证。
