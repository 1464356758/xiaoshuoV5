# 逐次写作与恢复协议（同日不限章数）

本工具不调用模型，沿用 V4.3 任务书、叙事审读、三轮修订、采用冻结和发布回执规则。不以新增文件或聊天中的完成声明代替真实成果。

无人值守执行先读《定时执行器.md》：默认由固定GitHub Actions执行器运行本文命令、保存归属和同步索引。下文是实际工具行为，不要求定时聊天必须能在本地下载仓库。新执行器请求不允许直接采用，finalize统一完成release-check、adopt与finish。单轮网络/工具失败保留目标，不自行暂停每日计划。

## 计划与反馈对话

每本小说复用一个实际建立的每日任务。修改时先按仓库和作品身份查已有任务，再更新；不能每天创建一个新计划。任务反馈可以固定在平台实际产生的任务对话中，作者已接受这种方式。个人端可登记实际反馈对话链接，方便直接打开，但保存链接不会改变平台投递位置，也不能证明已返回创建时的原对话。

实际模型及思考档位须由运行元数据或平台明确设置核实；工具不提供时写“未验证”。提示词要求认真、写“6.1”或回复较长都不能证明用了某个模型或深度思考。质量验收看完整正文、具体因果、真实引文、回看与问题处理，不用模型名代替。

## 首次进入每日任务

在当前小说仓库的最新默认分支工作，先确认远端提交头并回读当前状态，再运行：

```bash
python3 tools/daily_update.py --project . begin --trigger-id 本次写作请求稳定编号
```

- started：记录本次 run_id、目标章和前文基线。先将 book/daily/active.json 原子写回远端并回读，确认没有并发版本冲突，再开始正文。
- already_completed：同一个trigger_id已完成，重试不再开章；新的一条“下一章”指令使用新编号，当天即可继续。
- verify_in_progress：存在正在执行或中断的目标，先核实原执行是否停止；不能仅因超时自动抢占。
- recovered_completion：目标已经采用但回执尚未落盘（包括active已标完成但回执丢失，或回执已落盘而active尚未更新），按实际采用时间恢复并同步。不能将昨日采用日期改成今天。本次只保存和回读恢复证据，不顺便开下一章。
- 报错：如实处理。未选平台、未定题、尚无 canon/roadmap 或旧书没有冻结机制时，不绕过流程自动开写。

## 写作和完成

沿用原工作流准备资料、任务书、候选正文、写后记录、审读和 release-check，再 adopt。adopt 现在为新采用章记录 adopted_at；旧章不追补或改写采用日期。

实际读取上章、最近三章全文、近五章推进、相关事实与人物知情、开放承诺；不足三章就读全部已有章。到期全文回看必须在冻结前完成。写前任务书明确本章选择、代价和场景作用；写后从正文反提实际变化，比较全书类似办法。审核不能把摘要冒充原文，不能用批量填pass或降低字数、修订、叙事门槛赶完成。工具能约束版本、引文和流程，不能观察模型内在思考或保证文学判断。

```bash
python3 tools/daily_update.py --project . finish --run-id 实际执行编号
python3 tools/online_state.py --project . build-index
python3 tools/online_state.py --project . validate-index
```

finish 核对目标章、前文版本、冻结正文、章后记录及已使用的审查报告。每次完成回执按trigger_id写入book/daily/requests/编号摘要.json，active.json绑定实际receipt_path并标记完成。日期.json保留为当天第一份完成记录，兼容旧读取方式，不再限制后续章节。旧作者加更记录仍按原绑定核验。

将正文、状态、执行记录、回执和索引作为同一批更改写回。保留基础树，以预期分支头进行非强制更新。冲突后读取远端；旧 run_id 已被恢复执行替换时，旧执行不能继续写回。提交后回读正文、回执与状态，成功才能说已经完成。

写回前重新读取远端active的run_id与状态，确认仍是本次执行，不能仅比较本地副本。提交失败保留草稿和同一目标；不重新begin、重置修订次数或用另一工作区抢占。active写着running只是记录，不证明后台任务仍活着。

工具无法替你证明远端同步、实际阅读行为或文学质量。只在临时工作区完成，仍然不算已写入 GitHub。

## 中断和恢复

```bash
python3 tools/daily_update.py --project . block --run-id 实际执行编号 --reason '真实中断原因'
```

把中断状态同步回仓库。不得记录凭证、登录状态或其他秘密。常见 GitHub 凭证格式会被隐去，但不要把任意秘密交给 reason。

仅当原执行确实停止，作者或当前执行已经核实时，才运行：

```bash
python3 tools/daily_update.py --project . begin --resume-stopped
```

恢复保持原目标、开始日期、前文基线和核心任务的修订计数，更换本次 run_id 并保留上次尝试。先同步恢复记录再继续同一章，不直接开下一章。

由于 GPT 任务在不同临时工作区运行，程序本地锁不是跨机器锁。必须执行“记录远端原子保存并回读后才能写作”的协议。没有联网写入或并发冲突时就停止，不能以本地锁存在为理由继续。

普通手动创作不自动建立计划。平台实际发布仍使用原 publish 命令，必须有真实回执或作者明确确认；每日完成记录不是发布回执。

个人端1.3的“核验本日完成证据”是只读的独立入口，核对固定提交中的正文、冻结、审查与回执，并区分中断、缺失和读取失败。日常“今日更新”仍只看最新正式章节文件的北京时间提交日期，不增加日报或完成回执门槛。

## 同日不限章数

同一天不限章数；每次独立的“下一章”指令完成一章，可立即继续下一章。同次请求重试复用trigger_id，只接续或核验原章，不重复开章。 不传--trigger-id的直接手动begin视为一次新指令；GPT为可重试执行应主动固定本次编号，不能换编号重放同一指令。固定执行器自动按实际controller生成稳定编号；原平台运行ID相同，即使客户端重连也不重复开章。

日期仅用于标记实际采用时间。同一天可以有多个独立完成回执，已有日期回执和冻结前文保持原样。恢复旧目标仍优先，未完running不因新指令或超时被抢占。
